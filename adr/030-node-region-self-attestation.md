# ADR 030: Node Region Self-Attestation

**Date:** 2026-05-14
**Status:** Draft
**Amended:** 2026-06-17 (#801) — the ripening-window evaluation point is split by direction: the read/serve-time scope predicate stays at `block.timestamp`; the **slash-eligibility** predicate evaluates the window at the served `responseTs`. See [§ Region-stability window](#region-stability-window) and [§ Risks](#risks).

## Context

Each node declares a region — an ISO 3166-1 alpha-2 country code — at registration (`regionHint` on `CapacityBond`) and in every gossiped `NodeAnnounce` (the `region` field on the signed body; see [ADR 001 § NodeAnnounce](001-network.md#adr-001-network-topology-and-peer-mesh)). The declared region is load-bearing in four places:

- **Regional blacklist enforcement.** A node applies only blacklist entries that are global or match its declared region ([ADR 011 § Regional Scope](011-content-takedown.md#regional-scope)), and is slashable only for serving a hash blacklisted in its declared scope ([ADR 011 § Slashing](011-content-takedown.md#slashing)).
- **Gossip topic routing.** Nodes publish to the regional topic `cdn/region/{cc}/v1` alongside the global topic ([ADR 001 § Gossip Topics](001-network.md#adr-001-network-topology-and-peer-mesh)).
- **Peer-selection geo-diversity.** Clients prefer geographically diverse providers on ranking ties ([ADR 001 § Selection](001-network.md#adr-001-network-topology-and-peer-mesh), implemented in `crates/node/src/selection.rs`).

Three ADRs ([001 § Consequences](001-network.md#consequences), [011 § Regional Scope](011-content-takedown.md#regional-scope), [019 § Deferred & Open](019-node-onboarding.md#deferred--open)) name "a decentralized oracle or third-party attestation service" as the production mitigation against region misreporting, but specify no design — oracle choice, IP→region resolution, mismatch handling, slashing implications, and operator UX are all open. This gap is production-blocking: without a decision, regional compliance under [ADR 011](011-content-takedown.md#adr-011-content-takedown-and-hash-blacklisting) is structurally fragile, and the reactive blacklist-scope flip ([ADR 011 § Regional Scope](011-content-takedown.md#regional-scope)) remains open.

This ADR closes the gap by **rejecting** the oracle/attestation-service path and committing to self-attested regions as the production posture, with one protocol-level hardening — a region-change stability window — that removes the two region-flip surfaces that do not self-correct under the existing latency/reputation loop.

## Decision

### Self-attestation is canonical

A node's region is whatever the operator declares — at `CapacityBond.registerNode`, in `CapacityBond.updateRegion` calls ([§ Region-stability window](#region-stability-window)), and in every signed `NodeAnnounce` body. The protocol accepts it at face value: no on-chain or in-gossip IP-geolocation cross-check, no required third-party attestation signature. Gossip-layer validation in `crates/gossip/src/validation.rs:127-130` stays shape-only (any two-byte ASCII-uppercase value). [ADR 001 § Gossip validation](001-network.md#gossip-validation) describes a stricter known-code-set check; tightening `validation.rs` to enforce it is orthogonal and not a precondition — logged in Cross-ADR Impact, not silently carried.

### Soft mitigation: latency-vs.-claim reputation penalty (canonical)

The penalty in [ADR 001 § Consequences](001-network.md#consequences) — clients apply a reputation penalty when observed latency contradicts the claimed region (default heuristic: RTT > 150ms to a node in the same claimed region) — is the canonical continuous mitigation. It is self-correcting: a misdeclaring node loses payouts proportional to how badly its declared region contradicts measured RTT, with no new protocol surface. This ADR does not respecify the threshold, sample size, or decay curve; that tuning is a follow-up in the [ADR 008](008-reputation.md#adr-008-reputation-system) reputation domain, not a precondition here.

### Region-stability window

Two gaming surfaces are not addressed by the latency/reputation loop, because both pay off the instant a region is changed — faster than RTT sampling can tax the new claim:

- **Reactive blacklist-scope flipping** ([ADR 011 § Regional Scope](011-content-takedown.md#regional-scope)): a node serving a hash flips `regionHint` out of the entry's region the moment a regional blacklist entry lands, shedding both the obligation to drop the content and — under [ADR 011 § Slashing](011-content-takedown.md#slashing) — the regional slash exposure. Today nothing gates this.

A single protocol invariant — a region-change stability window — closes both.

**CapacityBond interface delta:**

- `regionLastChanged: uint256` (Unix seconds, matching `firstBondedAt` / `registeredAt` / `lastMultiaddrUpdate` in [ADR 003 § Data Structure](003-payments.md#data-structure)). Set to `block.timestamp` on every successful `updateRegion`; **not** written by `registerNode`, so it stays zero until the first region change. Eligibility checks read it through the `effective` fallback below, where `regionGateActivatedAt` is a single contract-global timestamp written once in the upgrade initializer that introduces this field. This avoids a per-record storage migration while staying conservative for the migration cohort: a pre-upgrade operator who changed region just before the upgrade does **not** inherit an ancient `firstBondedAt` that passes the window instantly — the window runs from gate activation, not original registration.
- `regionPrev: string` — the region in effect immediately before the most recent `updateRegion`. Set to `""` on `registerNode`, to the prior `regionHint` on every successful `updateRegion`. Read only while a change is unripened (`block.timestamp - effective < REGION_STABILITY_WINDOW`); ignored once the window elapses. Shares the `string` shape of `regionHint` (below).
- `updateRegion(string newRegion)`: mirrors the operator-callable, no-bond shape of `updateMultiaddrs` ([ADR 019 § NAT and Multiaddr Handling](019-node-onboarding.md#nat-and-multiaddr-handling); cooldown semantics in [ADR 003 § Multiaddr Update Policy](003-payments.md#multiaddr-update-policy)) — caller must be the operator's registered Ethereum address. **Reverts if `regionLastChanged != 0` AND `block.timestamp - regionLastChanged < REGION_STABILITY_WINDOW`** (cooldown equals the stability window). The `!= 0` guard exempts an operator's *first* region change from the cooldown, so a freshly registered operator can correct a mis-entered region without waiting a window. This is safe: reactive evasion is foreclosed by the blacklist-scope predicate below (the previous region's entries keep applying via `regionPrev`) regardless of the cooldown, whose sole job is preventing a *second* flip from outrunning the single `regionPrev` slot — and that second flip is gated because `regionLastChanged != 0` once the first change lands. A chain of rapid flips cannot outrun the window; at most one change is ever in flight, so `regionPrev` is unambiguous. On success it sets `regionPrev = <prior regionHint>`, `regionHint = newRegion`, `regionLastChanged = block.timestamp`, and emits `RegionUpdated(bytes32 indexed nodeId, string oldRegion, string newRegion)` — `indexed nodeId` matches every other `CapacityBond` event ([ADR 003 § Interface](003-payments.md#interface-additions-to-capacitybond)); the block timestamp is implicit in the log header, so a separate parameter would be redundant.
- `regionHint` keeps its `string` type and semantics, untouched. Blacklist entries are keyed by a `bytes32` packed region key ([ADR 011 § Region representation](011-content-takedown.md#contract-contentblacklist)); the conversion happens at the scope-check boundary, where the operator's declared string is packed left-aligned into `bytes32` and compared against the entry key. Keeping `CapacityBond` on `string` costs one packing step per check and keeps the operator-facing field ([ADR 003 § Data Structure](003-payments.md#data-structure)) human-readable in registry reads and events.

The amendment is keyed off an `effective` timestamp:

```
effective = operator.regionLastChanged != 0 ? operator.regionLastChanged : max(operator.firstBondedAt, regionGateActivatedAt)
```

**Blacklist scope and slash eligibility** ([ADR 011 § Regional Scope](011-content-takedown.md#regional-scope), [§ Slashing](011-content-takedown.md#slashing)). The scope predicate has the same three legs in both directions — a node is in scope for an entry iff the entry is global, OR `entry.region == regionHint`, OR (within the ripening window AND `entry.region == regionPrev`) — but the **evaluation point of the ripening window differs by direction** (#801):

- **Read / serve-time scope** (what a node must apply and refuse to serve now): the window is evaluated at **`block.timestamp`** (`block.timestamp - effective < REGION_STABILITY_WINDOW`). "What should I serve at this moment" is a present-tense question.
- **Slash eligibility** (was a *past* serve punishable): the window is evaluated at the served **`responseTs`** — the signed response timestamp the challenge is built on — not at challenge-submission `block.timestamp`. `effective` and `REGION_STABILITY_WINDOW` are in seconds but the signed response timestamp is microseconds (`responseTsUs`), so implementations MUST floor it first: `responseTsSec = uint64(responseTsUs / 1_000_000)`. The predicate is `elapsed < REGION_STABILITY_WINDOW` where `elapsed = responseTsSec >= effective ? responseTsSec - effective : 0` — a serve that *predates* the change (`responseTsSec < effective`, the common case: serve, then flip) saturates to `elapsed == 0`, is treated as in-window, and the serve-time (prev) region stays in scope. Implementations MUST saturate rather than compute the bare unsigned `responseTsSec - effective`, which would underflow on exactly that central case. `responseTs` is already the anchor for the entry-liveness check on the slash path (an entry is slashable only if live strictly *before* the serve), so the window now shares that anchor. Anchoring the punitive predicate to when the node actually served closes a governance-tunable evasion: otherwise a node could shed the prev-region slash leg by flipping region and stalling the challenge until `block.timestamp - regionLastChanged >= REGION_STABILITY_WINDOW` — reachable when governance widens the evidence-age window ([ADR 014 § Evidence Staleness](014-on-chain-verification.md#evidence-staleness), `MAX_EVIDENCE_AGE_US`) toward 30d while lowering the stability window toward its 3d floor (see [§ Risks](#risks)).

A region change adds the new region's entries immediately but does not drop the previous region's entries — or the slash exposure under them — until the change ripens. Combined with the `updateRegion` cooldown, a reactive flip after an entry lands buys nothing for a full `REGION_STABILITY_WINDOW`.

`REGION_STABILITY_WINDOW = 7 days` (governable, hard bounds `[3d, 30d]` per the [ADR 009](009-governance.md#adr-009-governance-model) safety-bound pattern). The *blacklist-scope* amendment is strict with no discretion path: the previous region's entries simply keep applying until the change ripens.

**Threshold rationale.** Seven days is short enough not to penalise an honest relocator unduly, and long enough that flipping region to shed a regional entry's obligations costs seven days of unservable old-region content plus seven days of latency-vs.-claim reputation in the *target* region. The 30-day upper bound matches the [ADR 028 § Hard caps and frequency limits](028-slashing-appeals.md#hard-caps-and-frequency-limits) `APPEAL_FILING_WINDOW` default; the 3-day lower bound prevents governance from defanging the invariant.

### Misdeclaration is operator legal exposure, not a protocol offense

The protocol provides regional blacklist scoping as a *compliance affordance for honest operators*, not forced enforcement against dishonest ones. An operator who misreports region to evade a regional takedown remains the physical party subject to their jurisdiction's content law — courts reach the operator through staked TOKEN, registered Ethereum address, and registered multiaddrs without protocol-level geolocation. This is the posture every L1 takes toward miner/validator location: protocol provides mechanism, jurisdictions provide enforcement.

The residual exposure decomposes into two cases:

- **Reactive misdeclaration (flip after an entry lands).** Foreclosed by [§ Region-stability window](#region-stability-window): the previous region's entries — and the slash exposure under them — persist for a full `REGION_STABILITY_WINDOW`, `updateRegion` is cooldown-gated, and on the slash path the window is anchored to the served `responseTs`, so the flip-then-stall variant gains nothing either.
- **Pre-positioned misdeclaration (false region from registration, before any entry exists).** *Not* prevented, and the window does not claim to. A node that has always declared `Y` while physically in `X` is, under [ADR 011 § Regional Scope](011-content-takedown.md#regional-scope) / [§ Slashing](011-content-takedown.md#slashing), simply out of scope for `X`-only entries — it sheds protocol slash exposure for region-scoped `X` takedowns. Misdeclaration *expands* slashing surface only when the disputed content is also globally blacklisted or blacklisted in the declared region; for the canonical evasion case (an `X`-physical operator declaring a clean `Y` to dodge an `X`-only takedown) the net effect is *less* protocol slash exposure, not more.

Backstops for the pre-positioned case are deliberately off-protocol: (a) declared-jurisdiction legal exposure; and (b) the latency-vs.-claim reputation penalty ([§ Soft mitigation: latency-vs.-claim reputation penalty (canonical)](#soft-mitigation-latency-vs-claim-reputation-penalty-canonical)) taxing the false `Y` claim continuously. No new slashing offense for "region misreporting" is introduced — there is no protocol-level ground truth to slash against, and inventing one would require the oracle dependency this ADR rejects.

### Privacy disposition unchanged

[ADR 017](017-privacy.md#adr-017-privacy-analysis) classifies self-reported region (P-03, P-12, P-13) as accepted T2 exposure: intentionally public for client selection, inherent to the discoverability of a CDN serving regional clients. This ADR does not change that. `regionLastChanged` is a timestamp, not new content, and is already implicit in the on-chain transaction history of `registerNode` / `updateRegion`; surfacing it as a structured field is a readability change, not a leakage change.

## Consequences

### Positive

- Closes the region-attestation gap with a concrete decision, resolving the "production mitigation: oracle" passages in [ADR 001](001-network.md#adr-001-network-topology-and-peer-mesh), [ADR 011](011-content-takedown.md#adr-011-content-takedown-and-hash-blacklisting), and [ADR 019](019-node-onboarding.md#adr-019-node-onboarding-and-bootstrapping-flow).
- No new external trust root and no new external dependency.
- Reactive blacklist-scope flipping becomes a protocol invariant rather than an unmitigated gap.
- Operator UX unchanged for honest deployments — VPN, anycast, mobile, and multi-region operators are not penalized by an IP-geolocation gate that would systematically misclassify them.
- Compatible with the existing on-chain surface: `updateRegion` follows the `updateMultiaddrs` shape ([ADR 019 § NAT and Multiaddr Handling](019-node-onboarding.md#nat-and-multiaddr-handling)), and `regionLastChanged` adopts the timestamp-field shape of `firstBondedAt` ([ADR 019 § Re-Onboarding after Deregistration or Auto-Ejection](019-node-onboarding.md#re-onboarding-after-deregistration-or-auto-ejection)) — with opposite mutability (written on every successful `updateRegion` vs. `firstBondedAt`'s write-once-on-first-registration).

### Negative

- The protocol cannot prevent a **pre-positioned** misdeclaring node (false region since registration, before any entry exists) from staying out of scope for the real region's entries. Reactive flipping is foreclosed by [§ Region-stability window](#region-stability-window), but a persistently false declaration is accepted at face value — the residual risk this ADR consciously accepts. Backstops are off-protocol (declared-jurisdiction legal exposure plus the continuous latency-vs.-claim reputation penalty), not protocol-level slashing: [ADR 011 § Slashing](011-content-takedown.md#slashing) routes slash eligibility under the *declared* region, which by construction never reaches a region the operator never declared.
- The 7-day window slightly raises the cost of legitimate relocation: an operator who moves keeps the previous region's blacklist obligations until the change ripens.

### Risks

- **Coordinated region-spoofing attack on a region's reputation.** A fleet of misdeclaring nodes could pollute regional gossip topics and depress the region's measured reputation. Bounded by (a) the latency penalty (attacker reputation collapses as fast as RTTs are sampled), (b) the capacity-bond cost per node ([ADR 026 § Capacity-bond curve](026-tokenomics.md#capacity-bond-curve)), and (c) gossip-bandwidth cost. Not free; self-correcting.
- **Governance-set `REGION_STABILITY_WINDOW` drift.** Lowering the window toward the 3-day floor weakens the blacklist-scope protection. The hard bounds `[3d, 30d]` per [ADR 009](009-governance.md#adr-009-governance-model) make this an above-the-line governance question rather than a silent regression; the floor was raised from 1d to 3d so the worst legal setting still keeps a flip uneconomic (see Threshold rationale).
- **Migration-cohort window.** Pre-upgrade records have no `regionLastChanged`; the `max(firstBondedAt, regionGateActivatedAt)` fallback treats every pre-upgrade operator as having changed region at gate activation, so each must wait one `REGION_STABILITY_WINDOW` past activation before a region change ripens for blacklist scope. (A pre-upgrade record's *first* post-activation `updateRegion` is cooldown-exempt — `regionLastChanged == 0` — but does not ripen until the window passes, so the exemption changes the call's timing, not the protection's.) A one-time, bounded cost accepted in exchange for not running a per-record storage migration; it errs conservative (no record passes the window instantly on a stale timestamp).
- **Serve-time slash window has two accepted edges.** Evaluating the slash-path ripening window at `responseTs` closes the flip-then-stall evasion of a prev-region entry, but two edges remain, both consciously accepted:
  - *Honest-relocator current-leg exposure.* The current-region leg (`entry.region == regionHint`) applies regardless of timestamp — declaring a region opts into its entries immediately. A node that served compliantly in `X`, then genuinely relocates to `Y`, is in scope for `Y`-region entries the moment it declares `Y`, including for an already-served blob also blacklisted in `Y`. Fully exempting the pre-relocation serve would require reconstructing the node's region *at* `responseTs` — multi-level region history — which the single `regionPrev` slot deliberately does not store; widening that storage is rejected on `CapacityBond` runtime-size (EIP-170) grounds. Backstopped by the evidence-age window ([ADR 014 § Evidence Staleness](014-on-chain-verification.md#evidence-staleness)), which bounds how stale a `responseTs` a challenge may carry.
  - *Multi-change prev-leg ambiguity.* `regionPrev` is a single slot and `updateRegion`'s cooldown equals the window, so at most one change is in flight for window purposes — but the evidence-age window can exceed `REGION_STABILITY_WINDOW` (governance may raise `MAX_EVIDENCE_AGE_US` toward 30d while the window floors at 3d), permitting ≥2 ripened changes between `responseTs` and the challenge. Then `regionPrev` no longer names the region held at `responseTs`, so the serve-time prev leg cannot be faithfully reconstructed for that older serve. This is the same single-slot limit the read path already lives with, not a new exposure; accepted as residual, with the evidence-age window as the backstop.

## Cross-ADR Impact

- Tightening the [ADR 001 § Consequences](001-network.md#consequences) latency-vs-claim reputation penalty (threshold, sample size, window, decay) is in scope for the [ADR 008](008-reputation.md#adr-008-reputation-system) reputation domain, not blocked by this ADR.
- Tracked spec/impl divergence: `crates/gossip/src/validation.rs` enforces only the shape check (two ASCII-uppercase bytes), not the [ADR 001 § Gossip validation](001-network.md#gossip-validation) known-ISO-3166-1-alpha-2 set check. Closing it is in scope for the [ADR 001](001-network.md#adr-001-network-topology-and-peer-mesh) gossip-validation domain — logged here so the gap is not silent.
- Contract-level `regionLastChanged` / `regionPrev` / `regionGateActivatedAt` / `updateRegion` (incl. the stability-window cooldown) land with the `CapacityBond` implementation; the [§ Region-stability window](#region-stability-window) interface spec is the canonical reference for that work.
