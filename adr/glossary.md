# Glossary

Terms used across multiple ADRs without inline definition.

## Wire protocol & content

| Term | Definition |
| --- | --- |
| **Blob** | A content-addressed byte sequence identified by its BLAKE3 hash. |
| **Chunk** | The BLAKE3 hash-tree leaf size (1024 bytes). iroh-blobs uses this for verified streaming; on-chain Merkle proofs for slash evidence reference this leaf size — see [ADR 002](002-content-addressing.md#adr-002-content-addressing) for the addressing scheme and [ADR 014](014-on-chain-verification.md#adr-014-on-chain-verification-for-slashing-evidence) for the slash-evidence verification flow. |
| **Hash sequence** | An ordered collection of blob hashes (iroh's equivalent of a directory/manifest). |
| **Namespace** | A publisher-owned `uint256` identifier for a content set and the unit of origin addressing: a `cdn/client/v1` request pairs a blob hash with the namespace its content is published under, and the DAO authorizes an origin operator set per namespace (so redundancy is a namespace-level property). `namespaceId == 0` names no namespace — no publisher, no authorized origins, served best-effort from cache/DHT. See [ADR 002 § Publisher Identity and Namespaces](002-content-addressing.md#publisher-identity-and-namespaces). |
| **Publisher** | An Ethereum address that owns at least one namespace in `PublisherRegistry`; status is acquired implicitly on the first `createNamespace()` call, with no separate registration step. Once governance has vetted the publisher wallet, that publisher seats and unseats the origin operators for its own namespaces directly ([ADR 011 § Origin Assignment Authority](011-content-takedown.md#origin-assignment-authority)). See [ADR 002 § Publisher Identity and Namespaces](002-content-addressing.md#publisher-identity-and-namespaces). |
| **NodeId** | An iroh public-key identifier; the on-wire identity of a node. Bound to an Ethereum address on-chain via EIP-712 signature in `CapacityBond.registerNode` ([ADR 001](001-network.md#adr-001-network-topology-and-peer-mesh)). |
| **Node** | A staked participant that caches and serves blobs. Some nodes are configured with an origin backend; others are pure caches. |
| **Client** | A lightweight QUIC endpoint that streams content and pays per MB. |
| **Origin-backed node** | A node configured with an S3-compatible object store (S3/R2/B2/MinIO), NFS mount, or local disk. Can serve any blob in that store, never experiences a true cache miss. |
| **ALPN** | Application-Layer Protocol Negotiation — identifies which protocol a QUIC connection uses (e.g., `cdn/probe/v1`, `cdn/client/v1`). |

## Payments

| Term | Definition |
| --- | --- |
| **Payment token** | The dual-currency model's settlement asset: the currency clients pay in and operators are paid in. The concrete asset is **USDC**, fixed at contract deployment (immutable, 6 decimals) — see [ADR 003](003-payments.md#adr-003-payment-model). This is the canonical term used throughout the spec for the pool-deposit, voucher, and fee-distribution currency; "USDC" appears only where a USDC-specific property is load-bearing (decimals, Circle counterparty risk, on-chain identifiers, swap pairs, dollar-denominated constants). |
| **Governance token** | The dual-currency model's bonding/governance asset. The concrete asset is **TOKEN**, the protocol's native fixed-supply (1B) `ERC20Burnable` — see [ADR 026](026-tokenomics.md#adr-026-tokenomics). "TOKEN" is used as the asset symbol/unit; "governance token" is the role term. Distinct from the payment token; never interchangeable. |
| **Pool** | One funded on-chain deposit (the `PaymentPool` escrow) that backs off-chain vouchers from many capped signers to many nodes. Three roles: the **owner** funds it, signs capabilities, and receives the reclaim; a **signer** authorizes vouchers up to a capped, expiring capability; a **provider** (node) delivers and redeems its own vouchers. Funded with the payment token; the owner closes and reclaims the unspent remainder after a grace window — see [ADR 003](003-payments.md#adr-003-payment-model). Identified by `poolId = keccak256(owner, poolNonce)`. |
| **Capability** | An off-chain, owner-signed authorization delegating a signer: `{signer, spending_cap, pool_id, expiry}`. Node-agnostic (valid at every node), registered on-chain once on the signer's first redemption. Bounds the signer to its `spending_cap` and retires it at `expiry` — see [ADR 003](003-payments.md#adr-003-payment-model). |
| **Voucher** | A signed off-chain payment message. The EIP-712 signed fields are `{poolId, signer, provider, amount, bytesDelivered, chainRoot, chunkPrice}` (`provider` names the payee node), carried on the wire alongside the signature. `amount` is the cumulative settlement anchor; `chainRoot` heads an optional hash chain that advances it between signatures, and a `chainRoot` of zero seals the voucher at exactly `amount`. The contract settles in a single token fixed at deployment, so the voucher carries no token field; the EIP-712 domain separator binds it to the one contract deployment. Node-addressed and valid only under the signature of its capability-authorized signer. See [ADR 003](003-payments.md#hash-chain-metering-payword). |
| **Chain root / preimage** | The hash chain that meters delivery between signatures ([PayWord](003-payments.md#hash-chain-metering-payword)). The payer commits `chain_root = keccak^255(seed)` in a voucher and releases `keccak^(255−k)(seed)` after chunk `k`. A released **preimage** is an unsigned bearer proof: it proves its own index by hashing forward to the root, costs one hash to verify, and is worth nothing outside the lane whose voucher names its root. Redemption resolves `claimed = amount + chain_index × chunk_price`. |
| **Payment chunk** | The payment quantum, `chunk_bytes` = 1 MiB — the price quantum, the meter tick, and the withholding bound at once. A protocol constant, sized by USDC's 6-decimal payability floor ([ADR 003](003-payments.md#chunk-sizing-and-the-payability-floor)). Distinct from **Chunk** above, which is the 1024-byte BLAKE3 hash-tree leaf. |
| **TOKEN** | The concrete governance token: the protocol's native fixed-supply (1B) ERC-20. Used for capacity bonding, governance, and slashing — see [ADR 026](026-tokenomics.md#adr-026-tokenomics). There is no ongoing TOKEN-denominated service emission; year-1 operator bootstrap is funded by off-chain USDC infrastructure subsidies per [ADR 026 § Bootstrap mechanism — pre-seed USDC](026-tokenomics.md#bootstrap-mechanism--pre-seed-usdc). |
| **USDC** | The concrete payment token. Fixed at deployment; all pool deposits, fee distribution, and the externally-raised pre-seed pool are USDC-denominated — see [ADR 003](003-payments.md#adr-003-payment-model), [ADR 026](026-tokenomics.md#adr-026-tokenomics). |

## Tokenomics & incentives

| Term | Definition |
| --- | --- |
| **Bond** | TOKEN deposited in `CapacityBond` proportional to declared bandwidth capacity: `bond = k × Mbps^α` (defaults `k=12.6`, `α=1.2`). The only TOKEN-side requirement on operators — no separate flat minimum stake — see [ADR 026 § Capacity-bond curve](026-tokenomics.md#capacity-bond-curve). |
| **CapacityBond** | The on-chain capacity-bonded operator-registry contract. Holds TOKEN bond, enforces `bond ≥ bond_required(declared_capacity)`, performs slashing, manages the NodeId↔Ethereum-address binding — see [ADR 026](026-tokenomics.md#adr-026-tokenomics) and [ADR 016 § Contract Inventory](016-contract-interactions.md#contract-inventory). |
| **App Incentives** | A 19%-of-supply (190M TOKEN) demand-side ecosystem bucket, Treasury-multisig administered; 20% unlocked at TGE, then 48-month linear. Funds publisher rebates and integration grants — see [ADR 026 § App Incentives](026-tokenomics.md#app-incentives). |
| **Slashing** | Punitive reduction of bonded TOKEN on detected protocol violations. Escalating tiers 5%/15%/50% by lifetime offense count. Under escrow-on-slash the slashed TOKEN is held in `CapacityBond` escrow until appeal finality, then distributed 50% challenger / 50% burn (or refunded to the operator on a granted appeal) — see [ADR 026 § Slashing and burn](026-tokenomics.md#slashing-and-burn). Any slash additionally stamps `CapacityBond.slashedAtEpoch[op]` per [ADR 036 § Slashing zero-out](036-served-bytes-voting-weight.md#slashing-zero-out), zeroing the operator's vote weight while that watermark falls inside the trailing window. |
| **`slashedAtEpoch`** | A `CapacityBond` per-operator watermark holding the max epoch among the operator's still-standing slashes: stamped by any `slash()` call and **recomputed** (internal `_recomputeSlashedAtEpoch`) by the `settleAppealGranted` escrow hook on a granted slash appeal via [ADR 028](028-slashing-appeals.md#adr-028-slashing-appeals-and-dispute-escalation), clearing to zero only when no slash stands. Read by `DecdnGovernor._getVotes` to zero an operator's vote weight while inside the trailing window — see [ADR 036 § Slashing zero-out](036-served-bytes-voting-weight.md#slashing-zero-out). |
| **`windowEpochs`** | The governable trailing-window size (in epochs) used by both `FeeRouter.bytesInWindow` (vote-weight numerator) and the slash-zero-out interval. Default 13 (~1 quarter at 1-week epochs); bounds `[4, 26]` — see [ADR 036 § Governable parameters with safety bounds](036-served-bytes-voting-weight.md#governable-parameters-with-safety-bounds). |
| **Served-bytes voting weight** | The governance vote-weight source under [ADR 036](036-served-bytes-voting-weight.md#adr-036-served-bytes-voting-weight): `vote_weight(op, t) = min(served_bytes_window(op, t), voteCapBps × total_bytes_window(t) / 10_000) × age_ramp(op, t)`, where `served_bytes_window(op, t)` is the trailing-`windowEpochs` sum of `FeeRouter.bytesPerEpoch[op]`. Zero while `CapacityBond.slashedAtEpoch[op]` falls inside the trailing window. `FeeRouter.bytesPerEpoch` is governance-canonical. |
| **Epoch** | The 1-week trailing-window unit. Per-operator `bytes_delivered` counters accumulate on the `FeeRouter` and are read both for the served-bytes voting weight ([ADR 036](036-served-bytes-voting-weight.md#adr-036-served-bytes-voting-weight)) and for trailing-window analytics. Counters do not drive bucket payouts (`FeeRouter` is fully same-tx). |
| **FeeRouter** | The settlement-time three-bucket USDC distributor. Split: 60 operator base / 30 burn / 10 treasury. All three legs transfer in the settlement transaction; no epoch buckets, no pull-claim windows — see [ADR 026 § FeeRouter split](026-tokenomics.md#feerouter-split). Per-operator `bytesPerEpoch` accounting on this contract is the governance vote-weight source per [ADR 036](036-served-bytes-voting-weight.md#adr-036-served-bytes-voting-weight). |
| **SlashAppeal** | The slash-appeal state machine contract ([ADR 028](028-slashing-appeals.md#adr-028-slashing-appeals-and-dispute-escalation)). The slashed operator (and only the operator — `msg.sender` must equal the operator recorded in the slash) files an appeal posting a TOKEN bond; the emergency multisig fast-tracks/rejects and the Governor grants/upholds. A failed appeal burns that separate appeal bond in full. Holds `SLASH_APPEAL_ROLE` on `CapacityBond` and drives its **escrow-on-slash** settle hooks (`markAppealOpen` / `settleAppealUpheld` / `settleAppealGranted`): slashed TOKEN is held in `CapacityBond` escrow until the appeal resolves, then distributed 50% challenger / 50% burn or refunded to the operator on a granted appeal (which also recomputes `slashedAtEpoch[op]` over the operator's remaining standing slashes per [ADR 036 § Slashing zero-out](036-served-bytes-voting-weight.md#slashing-zero-out)). Replaces the retired SafetyReserve ([ADR 026 § Slashing and burn](026-tokenomics.md#slashing-and-burn)). |

## On-chain enforcement

| Term | Definition |
| --- | --- |
| **`CapacityBond`** | The on-chain capacity-bonded operator-registry contract. Holds TOKEN bond, enforces `bond ≥ bond_required(declared_capacity)` via the lock-to-capacity curve `bond = k × Mbps^α`, performs slashing, manages the NodeId↔Ethereum-address binding. |
| **`SlashJudge`** | The on-chain contract that adjudicates all slashable offenses: verifies slash signatures, manages challenge bonds, runs the two-phase commit–reveal challenge flow, calls `CapacityBond.slash()` — see [ADR 014](014-on-chain-verification.md#adr-014-on-chain-verification-for-slashing-evidence). |
| **`BuybackBurner`** | The contract that swaps the 30% burn-bucket USDC into TOKEN via Balancer V3 80/20 weighted pool and burns the proceeds — see [ADR 003 § BuybackBurner](003-payments.md#buybackburner) and [ADR 018](018-liquidity-strategy.md#adr-018-liquidity-strategy-balancer-8020-pol). |
| **`PublisherRegistry`** | The on-chain registry of namespace ownership and lifecycle (create, transfer under timelock). Records who owns each namespace and stores no content hashes — the hash→namespace association is supplied off-chain by the requester at fetch time. See [ADR 002 § Contract: PublisherRegistry](002-content-addressing.md#contract-publisherregistry) and [ADR 016 § Contract Inventory](016-contract-interactions.md#contract-inventory). |
| **`OriginAssignment`** | The DAO's positive origin-authority contract: governance vets a publisher wallet once, after which that publisher seats and unseats origin operators for its own namespaces instantly. `namespaceId == 0` has no authorized origins. Cache-only serving stays permissionless; only the origin role is gated here. See [ADR 011 § Origin Assignment Authority](011-content-takedown.md#origin-assignment-authority). |
| **Slash signature** | An EIP-712 secp256k1 signature (`slash_sig`) on `ProbeResponse` / `StreamResponse`, used for on-chain slash evidence via `ecrecover` and as the message-body attribution signature for the paid-delivery path — see [ADR 014](014-on-chain-verification.md#adr-014-on-chain-verification-for-slashing-evidence). |
| **Challenge bond** | The 100 TOKEN amount a challenger must post when submitting slash evidence. Returned on successful slash. A reveal that fails verification reverts, so the bond is never transferred; there is no counter-evidence window and therefore no path that forfeits it after the fact — see [ADR 014 § Bond Handling](014-on-chain-verification.md#bond-handling). |
