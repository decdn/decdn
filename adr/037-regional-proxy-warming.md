# ADR 037: Latency-Driven Proxy Warming for Regional Locality

**Date:** 2026-05-30
**Status:** Draft

## Context

Content discovery is keyspace-routed — `cdn/dht/v1` places provider records and routes FIND_VALUE queries by XOR distance from the BLAKE3 hash ([ADR 022](022-content-discovery.md#adr-022--content-discovery-at-scale)). Demand, however, is geographic. The two coordinate systems are independent, so a node has no protocol path to learn that geographically-nearby clients want content that currently lives only in a distant region.

The canonical failure: a client near Tokyo requests blob `H` whose only holder is a London origin. Nodes near Tokyo never learn that local clients want `H`, so no nearby copy is ever made, and every Tokyo client pays inter-continental latency. Neither demand-learning path in [ADR 022 § Popularity Signals](022-content-discovery.md#popularity-signals-and-market-dynamics) surfaces this:

- **FIND_VALUE query frequency** accrues at the K nodes closest to `H` *in keyspace*, which are geographically uniform-random. The node that observes "`H` is in demand" is, with high probability, not near the clients generating the demand.
- **Local cache-miss serving** happens only on a node that itself received a request for `H`. Clients route to the RTT-nearest holder ([§ Client selection policy](#client-selection-policy-latency-driven-proxy-preference)), which is the London origin, so nearby cache nodes never receive the request, never record a miss, and never cache.

This is a cold-start locality trap: a nearby node cannot earn the traffic for `H` until it holds `H`, and it does not receive `H` until it has earned the traffic. The trap is self-clearing the instant *one* nearby copy exists — that node publishes a DHT STORE ([ADR 022 § STORE Flow](022-content-discovery.md#store-flow-cache-event--dht-publish)), a regional requester discovers it, its low RTT makes it the RTT-nearest pick, and subsequent demand reinforces it. The unsolved problem is bootstrapping the first regional copy.

A demand-broadcast layer (broadcasting per-region hash popularity so nearby nodes fetch a copy in advance) was weighed and rejected: it adds a new broadcast message type, a new poisoning surface, and a privacy surface over client request patterns ([ADR 017](017-privacy.md#adr-017-privacy-analysis)). This ADR instead bootstraps the first copy at selection time, as a side effect of ordinary paid delivery, with no new wire surface.

## Decision

A client that finds only distant holders for a cache miss routes its paid `cdn/client/v1` request *through a nearby bonded node that does not yet hold the blob*. That node fills the request by window-paced cache-miss pull-through, serving the client while caching the blob, and thereby becomes the first regional copy. The mechanism decomposes into a client-side selection policy and a node-side serving behavior, neither of which changes the wire format.

### Client selection policy: latency-driven proxy preference

On a cache miss for hash `H`, the client takes its candidates from its peer store or the on-chain registry ([ADR 039 § Source set and selection](039-multi-source-parallel-fetch.md#source-set-and-selection)) and assesses their RTT — from its RTT map, or by probing them if it wants fresh RTT or price (§ [Probe roles](#probe-roles-client-optional-node-to-node-load-bearing)). It then applies a proxy-warming pre-step before committing to a holder:

- **Trigger.** Proxy warming engages only when the best holder's RTT exceeds `proxy_warming.rtt_threshold_ms` (the holders are all distant) **and** the client's cumulative RTT map contains a bonded node whose measured RTT is lower than the best holder's by at least `proxy_warming.margin_ms`. If no measured candidate clears the margin, the client routes directly to the best holder — proxy warming is a no-op, never a gamble.
- **Candidate pool.** The bonded nodes in the client's registry-backed discovery set ([ADR 001 § Node Discovery](001-network.md#node-discovery-registry)), excluding the distant holders.
- **Ranking key is measured RTT only.** Self-attested `region` ([ADR 030](030-node-region-self-attestation.md#adr-030-node-region-self-attestation)) is not consulted. Round-trip time is ground truth and cannot be forged: a node that misreports its region to appear local simply exhibits a high measured RTT and is never selected as a proxy. The region-spoofing surface is therefore irrelevant to this mechanism by construction.
- **RTT source.** The client's per-peer RTT map (§ [Client RTT map and latency discovery](#client-rtt-map-and-latency-discovery)). A warming request itself yields a fresh RTT sample for the chosen proxy, refining future selection.
- **One proxy, not a fan-out.** The client routes the request to the single best candidate. Only one regional copy is needed; fanning out across several near nodes multiplies the cold-pull cost without improving the outcome.
- **Fallback.** If the chosen proxy declines, stalls, or fails, the client fails over to the next-best candidate and finally to the direct holder. The progress deadline is the client's ordinary pull stall budget (the same budget that bounds any node that accepts a request and then makes no progress), so a stalled proxy needs no proxy-specific timer. The fallback is transparent to the caller — no error is surfaced while a candidate remains. All candidates draw on the one shared payment pool ([ADR 003 § Decision](003-payments.md#decision)), where each provider is a distinct lane and a lane for a not-yet-paid provider opens nothing on-chain, so failing over escrows no new deposit; the client resumes the partial it already holds, so it re-pays nothing already delivered.

Proxy warming defaults on (`proxy_warming.enabled = true`) and is fully disableable. Because a declining or stalled proxy fails over transparently to the direct holder, defaulting on cannot regress a fetch. The only client-observable cost is a bounded one-request latency premium the first time a locale warms a given blob.

### Client RTT map and latency discovery

Proxy ranking depends on the client knowing its round-trip latency to bonded nodes that do **not** hold the requested blob — precisely the nodes the normal discovery path never contacts. The probe cache ([ADR 001 § Probe cache](001-network.md#probe-cache)) is a 15-second, hash-keyed cache of positive results, not a longitudinal latency record, and a fetch's probe round samples only the few candidates it shortlists. A client that kept no record across fetches would forget those samples and re-learn its nearby set on every fetch. The client closes this with a dedicated latency structure and an active discovery source.

- **Per-peer RTT map.** The client maintains a bounded `NodeId → (rtt_estimate_us, last_sampled_us)` map, separate from the probe cache: keyed by node rather than hash, EWMA-smoothed across samples, LRU-bounded (recommended ~4,096 entries), with entries re-sampled or evicted once older than `rtt_map.staleness_secs`. Every QUIC interaction with a bonded node contributes a sample — registry-bootstrap connections, `cdn/probe/v1` responses, and completed `cdn/client/v1` streams (warming requests included).
- **Persisted, unified store.** The RTT map is not an in-memory cache: the client persists it to a per-peer on-disk store under its data dir, one record per node, unified with the registry snapshot rather than kept as a separate cache — each record carries the node's identity (Ethereum address, region hint) alongside its latency and stats in one place. A record also carries `rate_per_mb` from the node's most recent probe or stream response, an unsigned hint the client stores for diagnostics only — selection ranks on measured RTT, never on the stored rate. It never substitutes for the signed `StreamResponse.rate_per_mb` a client actually pays against, gated by `--max-rate-per-mb` ("no surprise pricing" still holds). A short-lived client that closes and restarts keeps its map instead of rebuilding it from nothing.
- **Active latency discovery.** Passive samples are biased toward the small set of nodes the client already fetches from, so the client runs a bounded background latency sweep: it periodically issues `cdn/probe/v1` requests to un-sampled or stale discovery-set entries, breadth first then refresh. The sweep stays within the existing probe rate budget ([ADR 001 § Probe rate limits](001-network.md#probe-rate-limits)) — a few probes per minute map a client's nearby set within minutes of startup. Latency-discovery probes are RTT measurements, not demand: they carry a reserved sentinel hash (or are otherwise flagged) that nodes MUST NOT count toward any demand metric ([ADR 022 § Popularity Signals](022-content-discovery.md#popularity-signals-and-market-dynamics)), and `has_blob: false` is the expected response. This sweep is a deferred follow-up, additive on top of the persisted store: the store's samples come only from ordinary fetch traffic — a discovery session's registry read (identity for every returned node) and each fetch's probe responses and completed stream TTFBs (latency and price) — never from a dedicated un-fetched-node sweep.
- **Cold start.** Until the RTT map covers a node that beats the best holder by `proxy_warming.margin_ms`, the client routes directly to the best holder and proxy warming simply does not engage; it becomes available as the map fills. Only one warming-capable client per locale is needed to seed a blob: once that client warms a nearby copy and the copy publishes its DHT STORE ([ADR 022 § STORE Flow](022-content-discovery.md#store-flow-cache-event--dht-publish)), every subsequent client — cold or warming-disabled — discovers the near holder through the normal path. The bootstrap requirement is "at least one client per locale with a populated RTT map," not "every client."

### Probe roles: client-optional, node-to-node load-bearing

Under this mechanism, `cdn/probe/v1` serves two distinct purposes with different weight.

- **Node-to-node probing is load-bearing.** A node filling a request by pull-through must find an upstream that covers the range it needs: `has_blob: true` with a coverage bitmap spanning the wanted blocks, measured RTT to pick a fast source, `rate_per_mb` (the pulling node pays), and the signed `ProbeResponse` that makes upstream bait-and-switch slashable ([ADR 005 § `cdn/probe/v1`](005-protocol.md#cdnprobev1--latency-probe)). This is the FIND_VALUE → probe path of [ADR 022 § FIND_VALUE Flow](022-content-discovery.md#find_value-flow-cache-miss--dht-lookup); it resolves full holders and partial holders alike, each with a coverage bitmap, and the probe confirms fresh coverage before the pull commits a range to a source. All probe-derived slashing evidence originates here.
- **Client probing is optional.** A client need not probe before a `StreamRequest`: it routes to its RTT-nearest node (§ [Client RTT map and latency discovery](#client-rtt-map-and-latency-discovery)) and the node serves or pulls through. Price discovery moves to `StreamResponse.rate_per_mb` — the client accepts by sending the first voucher or disconnects and tries another node ("no surprise pricing", [ADR 005 § `cdn/client/v1`](005-protocol.md#cdnclientv1--paid-delivery-protocol)). In the warming path probing is moot: the proxy is a deliberate non-holder and answers `has_blob: false`. A client MAY still probe when it wants fresh RTT and coverage across multiple known holders, or wants to retain requester-side rate-manipulation slashing leverage — which is not required for correctness.

The only probing a probe-less client performs is the background latency sweep that maintains its RTT map (sentinel hash, no `has_blob` semantics). Per-request content confirmation is concentrated on the node-to-node path, where a full holder is genuinely required.

### Node serving: window-paced pull-through

A node that receives a `cdn/client/v1` `StreamRequest` for a blob (or byte range) it does not hold fills it by pull-through, pipelined against incoming payment:

- The node pulls from an upstream provider discovered via the normal `cdn/dht/v1` path, verifying each chunk against the root hash (transfer/verification granularity `pull_chunk_bytes`, default ~1 MB) and forwarding it to the client as it arrives, collecting vouchers as the client pays.
- The pull runs **ahead** of cleared payment — pipelined for throughput — but pauses whenever the per-request unrecouped frontier (`bytes pulled − bytes paid` for this stream) would exceed the ramped credit window ([ADR 003 § Credit window](003-payments.md#credit-window)), and resumes as vouchers clear. Exposure on a request the client abandons is therefore bounded to that window, not the whole blob, and it grows only as the client itself pays: with a nonzero `credit_ramp_divisor`, a non-paying request fronts at most about two chunks of speculative spend, never the fully-ramped ceiling. With `credit_ramp_divisor = 0` the window opens at `credit_max`, so a non-paying request fronts at most `credit_max` plus one pull-window floor. The window is what decouples the loss bound from throughput: a strict one-chunk-ahead coupling (pull chunk `N+1` only after voucher `N`) would serialize one upstream round-trip per chunk — ≈`blob_size / pull_chunk_bytes` RTTs, tens of seconds of added latency on a 100 MB blob over an inter-continental link — so the loss bound is a *byte window*, not a one-chunk lockstep.
- Pulled chunks are written to the local store as they arrive. iroh-blobs partial blobs and bao verified-streaming make a partially-held blob first-class: the node verifies and serves any chunk range against the root hash and records which ranges it holds. A node accumulates `H` across requests until it holds the blob in full.

Because per-request speculative exposure is a bounded, ramped window rather than the entire blob, implicit pull-through is cheap enough that **the `StreamRequest` itself is the trigger** — there is no warming flag, no `allow_pull_through` field, and no accept/decline handshake. A request for content the node lacks is the demand signal. This also makes the probe-to-evict race benign: a node that advertised `H`, was selected, then evicted `H` before the request arrives re-pulls the needed range and continues serving, rather than erroring.

The node's own upstream pull is an ordinary cache-miss pull against actual holders, so a proxy never chains its pull through another non-holding proxy.

### Origin-tier pull-through: ranged fetch + external outboard

The window-paced path above pulls from an upstream **peer**, which serves bao natively ([ADR 038](038-bao-verified-range-streaming.md#adr-038-bao-verified-range-streaming-on-cdnclientv1)) so any range verifies against the root `H` as it streams. The **origin tier** — the opaque S3/R2/B2/HTTP/filesystem backends a node is configured with — is different: an origin serves raw bytes by hash with no bao tree, so a node sourcing a cold blob from origin has historically had to fetch the **whole blob**, import it (materializing the outboard), and only then serve verified ranges. For a client that wants one byte range of a multi-gigabyte single-blob publish, that is whole-blob origin egress paid to serve a fraction of it.

A node MAY instead serve the range with a **range-scoped origin pull** when the origin publishes a sibling outboard:

- **Publishing convention.** Alongside the data object keyed by `H`, the origin publishes the blob's pre-order bao outboard (`iroh-blobs`' `IROH_BLOCK_SIZE`, 16 KiB groups) at the sibling key `{H}.obao4`. The outboard is content-derived and small — `O(n / 256)`, ≈0.4% of blob size (≈8 MiB for a 2 GiB blob). The publisher tooling already imports through `iroh-blobs`' `FsStore`, which builds this outboard as a byproduct ([ADR 038 § Context](038-bao-verified-range-streaming.md#context)); publishing it is an upload, not a new computation.
- **Ranged fetch.** To serve bytes `[a, b)` the node issues a ranged origin read for the data (`Range: bytes=a-(b-1)` / S3 `GetObject` range / `seek`) **and** a read of `{H}.obao4`. Framing the bao tree needs the blob's **exact** total size, and the `{H}.obao4` outboard alone does not pin it (the final 16 KiB chunk group's length is not in the tree). The serving node is the one that must *produce* `StreamResponse.total_bytes` and so cannot read it from its own response, so it obtains the size with a cheap, body-free origin metadata probe (HTTP `HEAD` → `Content-Length`, S3/R2/B2 `HeadObject` → `ContentLength`, filesystem `stat`) issued before the ranged read. The probed size is **not** a trusted input: a wrong size makes the bao range verification below fail against `H`, degrading to a whole-blob pull. A `Content-Encoding` metadata response (whose advertised length is the encoded, not canonical, size) is treated as unknown and likewise degrades — consistent with the ranged fetch rejecting compressed ranges (the S3 adapter refuses them explicitly; the HTTP adapter's exact-length gate plus bao verification reject them). The one extra `HEAD`/`HeadObject` on a cold miss is negligible against the whole-blob egress it avoids.
- **Verification is self-validating against `H`.** The node verifies the fetched range against the root `H` it already wants, using the supplied outboard, in one step (`bao-tree`'s range validation over a pre-order outboard anchored at `root = H`). The outboard is **untrusted**: a tampered outboard, a tampered data range, or a wrong root all fail verification, because every parent hash must chain up to `H` and every leaf must hash to its anchored parent. There is no trusted-origin assumption — the origin is a dumb byte store, exactly as for whole-blob pulls ([ADR 002 § Content Addressing](002-content-addressing.md#adr-002-content-addressing)). The node writes the verified range into its store as a partial blob and serves it onward as bao per [ADR 038 § Serve side](038-bao-verified-range-streaming.md#serve-side).
- **Fallback is always correct.** When the origin does not publish `{H}.obao4`, does not honor `Range` (no `206`), or the outboard is absent/short, the node degrades to the existing whole-blob origin pull — import, materialize the outboard, then serve ranges. The optimization is a cost reduction on the origin hop; its absence is never a correctness or availability failure.

### Origin-tier whole-blob miss: stream-while-store

A **whole-blob** cache miss (`byte_offset == 0`, no `byte_len` bound) against an origin that publishes `{H}.obao4` follows a parallel optimization to the ranged case above, with the same outboard but a different shape: rather than importing the entire blob before serving any of it, the node streams origin plaintext straight to the paying client while teeing the same bytes into its store, so time-to-first-byte does not wait on the whole transfer.

The node fetches `{H}.obao4` once and drives a streaming bao encoder over the origin's plaintext byte stream, producing header-less bao wire incrementally rather than requiring a materialized outboard on disk first. That wire feeds the same window-paced, voucher-gated serve loop the node-to-node pull-through path uses (§ [Node serving: window-paced pull-through](#node-serving-window-paced-pull-through)) — payment pacing, the unrecouped-frontier bound, and client-abandonment handling are identical regardless of whether the bytes originate from a peer or from this tier. Verification is the same self-validating check against `H`: tampered origin bytes or a tampered outboard fail bao verification mid-stream rather than completing, and the partial, unverified bytes already teed to the store are never committed as a valid local copy.

This path applies only to unbounded whole-blob requests; a bounded/ranged request stays on the range-scoped origin pull above. When the origin publishes no `{H}.obao4`, a whole-blob miss falls back to the existing buffered path — import the whole blob, then serve — the same always-correct fallback framing as the ranged case.

Range-scoped origin pulls only **tighten** the exposure bound above: the bytes counted against the ramped credit window are the bytes actually pulled `[a, b)` plus the small outboard, not the whole blob — the same window, a smaller pulled side. The SSRF/redirect hardening on origin fetches applies unchanged to **both** the ranged data request and the `{H}.obao4` request: redirects stay disabled and the host allow-list is enforced on every request.

Speculative pull-through's economic exposure is bounded by the single ramped credit window ([ADR 003 § Credit window](003-payments.md#credit-window)), not a separate node-wide or per-peer cap: the window pacer is the whole admission story, and it is not a content-authorization mechanism — the cache role is permissionless, and the request `namespaceId` is a routing hint, not a trust anchor ([ADR 002 § Hash-to-namespace association](002-content-addressing.md#hash-to-namespace-association)). A node serves any hash it can produce (from its store or a configured origin) to any paying, pool-owning requester; unvetted content is kept out by [`ContentBlacklist`](011-content-takedown.md#adr-011-content-takedown-and-hash-blacklisting) (already-held content), not by inspecting which namespace a request names.

### Loop closure

Pull-through populates the node's cache, which fires the existing DHT STORE on blob commit ([ADR 022 § STORE Flow](022-content-discovery.md#store-flow-cache-event--dht-publish)). The node becomes a discoverable holder for `H`; the next regional requester discovers it, measures its low RTT, and selects it outright as the RTT-nearest holder. Proxy warming stops engaging for `H` in that locale once a copy exists.

For partial or range-access patterns where the node holds only some blocks of `H`, its STORE advertises the coarse coverage it has ([ADR 022 § Range-keyed partial-holder discovery](022-content-discovery.md#range-keyed-partial-holder-discovery)), so the node is discoverable for the ranges it serves as well as reachable by RTT routing. Loop closure does not depend on holding the whole blob.

### DHT advertising is range-keyed

A node publishes a DHT STORE for `H` once it holds ≥1 verified 64 MiB block, carrying a coarse coverage bitmap ([ADR 022 § Range-keyed partial-holder discovery](022-content-discovery.md#range-keyed-partial-holder-discovery)). A partial holder is discoverable for the blocks it covers, so a warmed fragment is serving supply that FIND_VALUE returns, not a dark copy reachable only by RTT routing. The bitmap on the record is a stale routing hint; the `cdn/probe/v1` coverage is the fresh authority a requester confirms against before it commits a lane.

### Parameters

| Parameter | Default | Purpose |
|-----------|---------|---------|
| `proxy_warming.enabled` | `true` | Master switch for the client-side proxy preference. |
| `proxy_warming.rtt_threshold_ms` | `150` | A best-holder RTT above this marks the holders as distant enough to warrant warming. |
| `proxy_warming.margin_ms` | `30` | A candidate proxy must beat the best holder's RTT by at least this margin to be chosen. |
| `rtt_map.staleness_secs` | client-set | Age past which a per-peer RTT entry is re-sampled or evicted. |
| `pull_chunk_bytes` | ~1 MB | Chunk transfer/verification granularity (bao verified streaming). |
| `credit_max`, `credit_ramp_divisor` | operator-set, finite ([ADR 003 § Credit window](003-payments.md#credit-window)) | The ramped credit window: max `pulled − paid` bytes for a lane, floored at one chunk (1 MiB, `CHUNK_BYTES`) and ramping toward `credit_max` as the lane pays. Bounds per-request abandonment loss while keeping the upstream pull pipelined — decouples the loss bound from throughput. |

The progress deadline for the fallback is the client's ordinary pull stall budget, not a proxy-specific timer. The load-bearing commitment for the credit window is that its floor is finite (so per-request loss is bounded) yet large enough to keep the upstream pull pipelined, and that `credit_max` is finite.

### Implementation status

The node-side serving behavior of this ADR — the window-paced pull-through handler — lives in the `crates/node/src/handlers/client/` module (`window.rs`: `serve_via_window_pull_through` / `window_forward_loop`). It fuses a progressive upstream pull (`crate::client_requester::open_progressive_pull`, driven via `crate::node_origin::NodeOrigin::open_progressive_pull`) with downstream delivery: each upstream chunk is forwarded to the paying client and tee'd into the cache (`decdn_cache::CacheEngine::open_tee_sink`), and the pull pauses whenever the per-request frontier `bytes_pulled − bytes_paid` reaches the ramped credit window, resuming as the client's vouchers clear. The pull leg's `decdn_client_pull::RampPacer` computes that same window from the stream's own paid frontier via `decdn_incentive::ramped_credit_window` ([ADR 003 § Credit window](003-payments.md#credit-window)), so the upstream pull and the downstream serve loop ramp in lockstep — with a nonzero `credit_ramp_divisor`, a non-paying client fronts at most about two chunks of speculative upstream spend, never the fully-ramped ceiling. With `credit_ramp_divisor = 0` that bound is `credit_max` plus one pull-window floor. The two windows count different bytes: the serve loop meters wire bytes, and the pull paces on the paid content frontier. As a result, the pull window can close while the serve loop still has credit room. The serve encoder then waits on a leaf or a proof node that only the pull can fetch, and it collects no voucher while it waits. To keep both legs live, the serve loop records the content offset the encoder waits on as the **serve demand**, but only when the serve loop has no encoded bytes left to send. The encoder reads ahead of the serve loop, and a wait with encoded bytes still buffered is not a stall. The encoder waits on the first byte that the pull has not fetched, so the demand is at most one chunk group past the pull frontier. The pull then fetches one more pull-window floor (one chunk plus three chunk groups) past its own window. The pull ignores a demand that is further ahead, because that demand comes from a serve leg that the pull does not block. A serve leg waits on the pull only while its own credit window has room, so a client that stops paying stops the demand. The serve demand therefore adds at most one pull-window floor to the speculative spend. A complementary **pre-flight deposit guard** composes in front of the window: a cache-miss pull is refused outright (signed `NotFound`, metered as `serve_stream_rejected_insufficient_deposit`, or as `serve_stream_rejected_signer_floor_at_cap` when the pool is solvent and the requesting signer has filled its share of the floor) when the requesting pool's remaining deposit cannot cover the worst-case blob cost. With a finite `max_blob_size_bytes` the ceiling is the whole-blob cost; when the size cap is unbounded (`0`) the guard falls back to the per-request window cost (the ramp floor, one chunk) rather than failing open — disabling the size cap must not silently disable deposit protection. The **direct-serve** path carries the same guard against a narrower ceiling — `min(credit window, chunk-group-aligned request span)`, which bounds what it can deliver before the first voucher clears to that window plus one chunk.

Deposit protection is applied in two layers, both genuinely pre-spend. `serve_stream` applies a **floor** — one credit window's cost against remaining headroom, capped by the request's own span when it bounds itself — above *every* cache-miss fill tier, so no tier fronts origin egress or upstream USDC for a pool that cannot pay for one window. The window tier's pre-flight reservation is exactly that same floor; in-stream exposure is bounded by the ramped credit window plus one serve-demand pull-window floor, which the serve loop and the pull-leg `RampPacer` enforce. **Residual:** an unbounded request (whole blob, or a tail) is priced at a whole window because its billed size is unknowable before the fill, so a cold sub-window fetch is refused where the same blob served warm would be priced at its actual span. And a pool funded for exactly one window can still trigger a whole-blob buffered node-to-node pull costing more than it can repay — that tier's real bound is `cache.max_blob_size_mb` as the engine enforces it, which the handler's floor does not price. Both are tracked separately.

The client RTT map and probe-less routing (§ [Client RTT map and latency discovery](#client-rtt-map-and-latency-discovery)) live in `crates/client-pull/src/peer_store.rs` (`PeerRecord`, `PeerStore`) and the CLI's `crates/cli/src/commands/fetch.rs`. `PeerStore` holds one JSON file per node under the client data dir, keyed by `NodeId`, with atomic temp-write-then-rename so concurrent `decdn fetch` processes never observe a torn record; `PeerRecord` carries identity (`eth_address`, `region_hint`, `identity_seen_at_secs`) and stats (`latency_ms`, `rate_per_mb`, `last_sampled_at_secs`, `sample_count`, `last_failure_at_secs`) in the same record, EWMA-smoothed and LRU-capped. `store_fast_path` consults the store first: when it holds enough fresh, non-suppressed candidates it selects and routes without a probe, taking price from the eventual `StreamResponse`; otherwise `discover_provider` falls through to registry discovery and probing within the same fetch. A discovery session upserts identity for every registry-returned node, and both probe responses and completed stream first-byte timing feed latency/price samples back into the store off the fetch's critical path (`spawn_harvest`). A `--rediscover` flag forces the discovery/probe path while still updating the store, and an optional `[client] region_allowlist` pre-filters candidates during discovery. The background latency sweep over un-fetched nodes (§ [Client RTT map and latency discovery](#client-rtt-map-and-latency-discovery)) is not implemented; the store fills only from ordinary fetch traffic.

Scoped deferrals tracked as follow-ups (this ADR remains the design they implement):

- **Active background latency sweep** — specified in [§ Client RTT map and latency discovery](#client-rtt-map-and-latency-discovery). The persisted store and probe-less routing are implemented and fill the map from ordinary fetch traffic (registry reads, probes, completed streams); a dedicated sweep that probes un-fetched, stale discovery-set entries with a sentinel hash is not.
- **Partial-blob (bao range) store and serving** — specified in [ADR 038](038-bao-verified-range-streaming.md#adr-038-bao-verified-range-streaming-on-cdnclientv1). The window-paced tiers pull and tee the whole blob on a whole-blob request (`byte_offset == 0` and `byte_len == 0`; a bounded request stays off the window loop, which would otherwise over-deliver and over-bill the whole blob) and verify the whole-blob BLAKE3 incrementally, whether the bytes arrive from a peer upstream or from the node's own origin (§ [Origin-tier whole-blob miss](#origin-tier-whole-blob-miss-stream-while-store)). A *resumed* cache-miss request (`byte_offset > 0`) that the range-scoped origin pull below does not serve — the source is a peer, or the origin publishes no `{H}.obao4` or honors no `Range` — falls back to the buffered whole-blob path. Range-addressed availability in `cdn/dht/v1` is carried by the coverage bitmap (§ DHT advertising is range-keyed).
- **Range-scoped origin pull** (§ [Origin-tier pull-through](#origin-tier-pull-through-ranged-fetch--external-outboard)) — **landed**. The `Range`-data + `{H}.obao4` optimization, its bao verification, and the whole-blob fallback ship on the cache engine's `Origin` adapters (`decdn_cache::CacheEngine::pull_through_range` / `range_pull_attempt`, the HTTP/S3/filesystem `fetch_range` impls) independently of the node→node window path. The `cdn/client/v1` handler wiring also landed: a bounded/offset cache-miss `StreamRequest` (`byte_len > 0` or `byte_offset > 0`) runs `try_range_pull_through` (`crates/node/src/handlers/client/fill.rs`, dispatched from `dispatch.rs`) — origin size probe (`CacheEngine::origin_size` over the new `Origin::size`) → `pull_through_range` → serve the partial via `CacheEngine::export_bao_range_stream` — before the whole-blob fallback, gated on the same `pull_authorized` ownership check. End-to-end coverage of the cold ranged path is in `crates/node/tests/origin_range_pull.rs`.
- **Pipelined look-ahead beyond one chunk.** The window is honored as a byte bound — the *pull* runs ahead by the full ramped credit window, but downstream payment proofs are collected one chunk at a time (one per serve-loop iteration), so payments are recouped serially: a fully-ramped window well above one chunk bounds exposure as specified but does not yet overlap multiple in-flight chunk payments. Under PayWord the per-iteration proof is a `ChunkPreimage` rather than a signed voucher ([ADR 003 § Hash-chain metering (PayWord)](003-payments.md#hash-chain-metering-payword)), which removes the per-iteration signature but not the serialization.

The window-paced handler introduces no wire-format change: its `StreamRequest` / `StreamResponse` surface and `cdn/client/v1` framing are unchanged. The origin-tier path (§ [Origin-tier pull-through](#origin-tier-pull-through-ranged-fetch--external-outboard)) separately consumes the optional `StreamRequest.byte_len` bound added by [ADR 005 § Bounded byte ranges](005-protocol.md#bounded-byte-ranges) — an absent/zero value is the unchanged whole-tail default — off the same message; see the [Cross-ADR note](#cross-adr-impact) below.

## Consequences

### Positive

- Closes the regional-locality cold-start trap with no new wire surface and no demand-broadcast layer — the warming request is ordinary paid delivery.
- Region self-attestation ([ADR 030](030-node-region-self-attestation.md#adr-030-node-region-self-attestation)) is sidestepped entirely: proxy selection ranks by measured RTT, so a misdeclared region cannot attract warming traffic.
- Window-paced pull-through bounds speculative loss for *every* cache-miss serve, not only warming requests — it is independently valuable to the node-to-node delivery path.
- The self-reinforcing DHT + selection-score loop is unchanged; this mechanism only seeds it, then disengages.
- Costs fall where the benefit lands: the first client in a locale absorbs a bounded one-request latency premium, and every subsequent local client is served from a warm nearby copy.

### Negative

- The first client to warm a locale for a given blob pays a latency premium (one extra hop plus the cold upstream pull's start-up latency) relative to going direct. The premium is bounded by the client's pull stall budget and the fallback path.
- A warmed node that holds `H` only partially publishes a STORE carrying its coverage bitmap, so such copies are discoverable via the normal FIND_VALUE path for the blocks they cover, as well as reachable by RTT routing.
- The per-peer RTT map and background latency sweep are new always-on client state and traffic. The sweep is bounded by the existing probe rate budget, but it is a real cost a warming-capable client pays continuously. The persisted store means a returning client keeps its map across restarts, but a genuinely new client, or one whose store has not yet populated, warms nothing until the store fills; until then it falls back to direct delivery.
- Speculative pull-through that the pre-flight deposit guard refuses, because the requesting pool cannot cover even the ramp floor, leaves that warming opportunity unserved; this is the intended trade against operator loss.

### Risks

- **Manufactured-demand routing.** A client can route warming requests toward content it chooses, forcing nodes into speculative pulls. Bounded by the ramped credit window plus one serve-demand pull-window floor — with a nonzero `credit_ramp_divisor` a non-paying stream fronts at most about two chunks, and the exposure never exceeds `credit_max` plus one pull-window floor regardless of how many peers or hashes the demand spreads across — and by the fact that the node is paid for bytes it serves. Not free; self-limiting.
- **Parameter drift.** A `credit_max` set too high, or a `credit_ramp_divisor` set too low, widens the speculative-loss surface; set too tight, warming rarely engages and locality does not improve. The defaults are modeled before locking and are operator-tunable.
- **RTT-map coldness.** A client with sparse RTT history may not yet know its genuinely-nearest node and may warm a sub-optimal but still-closer proxy. This is self-correcting: each request adds RTT samples, and any copy closer than the distant holder still improves locality and feeds the discovery loop.

## Cross-ADR Impact

- [ADR 001 § Node Selection Algorithm](001-network.md#node-selection-algorithm): selection gains a client-side proxy-warming pre-step that may route a request to a measured-nearby non-holder; the unified selection score is the node pull-leg ranker, and the client does not compute it. The generic FIND_VALUE → probe → select content-discovery flow carries a client-path carve-out: a client MAY skip per-request probing and route by its RTT map, taking price from `StreamResponse` (§ [Probe roles](#probe-roles-client-optional-node-to-node-load-bearing)); the node-to-node pull-through path retains the full probe flow. The per-peer RTT map and background latency sweep (§ [Client RTT map and latency discovery](#client-rtt-map-and-latency-discovery)) are new client-side state and behavior beyond the 15-second hash-keyed probe cache; this ADR is their canonical specification.
- [ADR 005 § Wire Protocol](005-protocol.md#adr-005-wire-protocol): the `cdn/client/v1` node handler fills a request for an unheld blob/range by window-paced pull-through pipelined against vouchers. This extends the cache-miss serving behavior, where a node lacking the blob and an origin for it returns `NotFound`: under this ADR a node MAY instead pull through from the network to serve, subject to its ramped credit window, returning `NotFound` only when no provider is reachable or it declines. The window-paced node→node path needs no message-format change — `StreamRequest.byte_offset` already expresses resumption and iroh-blobs verified streaming supports incremental chunk verification. The origin-tier optimization (§ [Origin-tier pull-through](#origin-tier-pull-through-ranged-fetch--external-outboard)) consumes the **bounded** range bound `StreamRequest.byte_len` added by [ADR 005 § Bounded byte ranges](005-protocol.md#bounded-byte-ranges) so a node can scope its origin fetch to exactly `[byte_offset, byte_offset + byte_len)`. The handler is described in § [Implementation status](#implementation-status); this ADR is the design it implements.
- [ADR 012 § Client Architecture](012-client.md#adr-012-client-architecture-bootstrap-and-trust-model): clients implement the latency-driven proxy-preference policy and the per-peer RTT map with background latency discovery (§ [Client RTT map and latency discovery](#client-rtt-map-and-latency-discovery)) that ranks candidates. Per-request probing becomes optional for clients (§ [Probe roles](#probe-roles-client-optional-node-to-node-load-bearing)): the default path is probe-less RTT-map routing with price taken from `StreamResponse`.
- [ADR 022](022-content-discovery.md#adr-022--content-discovery-at-scale): this mechanism is the locality complement to keyspace-routed FIND_VALUE discovery; it reuses the STORE-on-commit loop for closure. Realized demand is served reactively here — the sole content-propagation path alongside operator pinning. The on-chain origin directory it shares with [ADR 022 § FIND_VALUE Flow](022-content-discovery.md#find_value-flow-cache-miss--dht-lookup) is used only to *route* a namespace-hinted request to candidate origins, never to authorize a serve.
- [ADR 030](030-node-region-self-attestation.md#adr-030-node-region-self-attestation): proxy selection deliberately uses measured RTT rather than the self-attested region field, so this mechanism neither relies on nor strengthens region attestation.

## Acceptance Criteria

1. A client whose probed holders all exceed `proxy_warming.rtt_threshold_ms`, and whose RTT map contains a bonded node beating the best holder by `proxy_warming.margin_ms`, routes its `StreamRequest` to that nearer non-holder; with no qualifying candidate it routes directly to the best holder.
2. Proxy candidate ranking is invariant to peers' self-attested `region` values — selection depends only on measured RTT.
3. A node filling a request for an unheld blob pulls ahead of cleared payment in a pipeline, pausing when `pulled − paid` for the request reaches the ramped credit window; on client abandonment its unrecouped speculative spend is at most that window, and the upstream pull is not serialized to one round-trip per chunk.
4. The ramped credit window widens only as the request's own stream pays: a non-paying stream stays pinned at the one-voucher-interval floor, and a paying stream ramps toward `credit_max` in proportion to `paid`, while continuing to serve ranges already held.
5. After a warming serve completes the blob, the node publishes a DHT STORE for `H`, and a subsequent regional FIND_VALUE returns the node as a holder.
6. A proxy that declines or stalls past the client's pull stall budget causes the client to fail over to the next candidate and then the direct holder, with no error surfaced to the caller; the client records the observed RTT regardless of outcome.
7. A node's upstream pull for a warming request targets actual holders via the normal `cdn/dht/v1` path and is not itself routed through another non-holding proxy.
8. The client maintains a per-peer `NodeId → RTT` map distinct from the hash-keyed probe cache, populated by passive sampling on every QUIC interaction and by a bounded background latency sweep that stays within the probe rate budget.
9. Latency-discovery probes carry a reserved sentinel hash (or equivalent flag) and are not counted toward any node's demand metrics.
10. A client whose RTT map covers no node beating the best holder by `proxy_warming.margin_ms` routes directly to the holder; warming engages only once such a node is mapped, and a single warmed copy makes subsequent clients in the locale resolve the near holder through the normal discovery path.
11. A probe-less client issues a `StreamRequest` without a preceding per-request probe, takes the rate from `StreamResponse`, and accepts by sending the first voucher or disconnects; a node-to-node pull-through always performs the full FIND_VALUE → probe flow against full holders and retains its signed-probe slashing evidence.
12. A ranged cache-miss serve against an origin that publishes `{H}.obao4` fetches only the requested `[a, b)` data plus the outboard, verifies the range against the root `H` with the untrusted outboard (rejecting a tampered range, a tampered outboard, or a wrong root), and counts only the pulled bytes against the ramped credit window; an origin without the outboard or without `Range` support degrades to a whole-blob pull with no correctness or availability change.
13. A whole-blob cache-miss serve (`byte_offset == 0`, no `byte_len` bound) against an origin that publishes `{H}.obao4` forwards origin bytes to the paying client and tees them into the store at the same time, so the client receives bytes before the whole blob lands, under the same window pacing, voucher cadence, and deposit guard as the node-to-node pull-through path. Tampered origin bytes or a tampered outboard fail verification mid-stream and leave no committed local copy. An origin that publishes no `{H}.obao4` degrades to the buffered import-then-serve path with no correctness or availability change.
