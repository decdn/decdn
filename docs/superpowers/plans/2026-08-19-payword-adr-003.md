# Land PayWord (hash-chained per-MB meter) into ADR 003 — issue #1670

## Context

Today a paying client signs one EIP-712 voucher every 4 MiB. That costs a secp256k1
signature per interval on the buyer's CPU and forces the seller to advance durable lane
state before it may deliver further bytes. PR #1652 proposed fixing this with **PayWord**
(a hash chain that meters delivery between signatures) but bundled a second, unrelated
decision — best-effort async voucher persistence — and edited ~17 ADRs. It was closed and
split. Both siblings have since merged: credit slow-start (#1669 → #1691) and async
voucher persistence (#1672 → #1706). **#1670 is the last piece, and it is documentation
only.**

The outcome: ADR 003 documents one voucher whose cumulative `amount` is the settlement
anchor, plus an *optional* hash chain that advances that anchor without a signature.
Redemption is one formula — `claimed = amount + chain_index × chunk_price`. A per-chunk
payment tick costs one keccak instead of one signature, with nothing to acknowledge and
nothing to fsync.

A prior attempt exists (PR #1692, branch `docs/1670-payword-adr-003`, commit `e29de67a`,
closed unmerged). **Per decision, this plan does not reuse its text.** The ADR prose is
written clean against issue #1670 and against current `main`, which has moved 40 commits
past that branch — `redeemMany(PoolBatch[])`, skip-not-revert batch semantics, the ramped
credit window, and the frontier/redeemed persistence split all postdate it. The follow-up
implementation issues it filed (#1693 contracts, #1694 incentive, #1695 protocol) are
closed and will be re-filed.

## Scope

**Documentation only.** No Rust, no Solidity, no tests. Implementation is re-filed as
three follow-up issues at the end.

## Settled design parameters

| Parameter | Value | Rationale |
|---|---|---|
| `chunk_bytes` | 1 MiB (1,048,576 B), protocol constant | USDC has 6 decimals; a chunk must price to ≥ 1 base unit. 1 MiB is ~10 units at the $0.01/GB target and still 1 unit at the $0.001/GB floor. 100 KB is unpayable at the floor. |
| `chunk_price` | ≡ the node's advertised `rate_per_mb` | `CHUNK_BYTES == BYTES_PER_MB`, so no second price constant and no new governance knob — the payability floor *is* the existing `deliveryFloor`. Stays a signed voucher field so redemption never depends on a rate that moved after signing. |
| `MAX_CHAIN_LENGTH` | **255** | `chain_root = keccak^255(seed)`; releasable indices `1..=255` encode directly in the one wire byte with no offset, so no off-by-one can exist. Index `0` is the redeem-time settlement case and never travels the wire. **Deviates from the issue body's 256** — call this out in the PR description. |
| Chain epoch | 255 MiB per chain | One signature per rollover; ~4× more than a 1024-chain, traded for a fixed 33-byte wire message and a ≤255-hash worst-case walk. |
| Wire encoding | `preimage ‖ index`, 33 bytes, no length prefix | Index placement is what lets several concurrent streams share one lane and one chain. |
| Sealed voucher | `chain_root = 0`, redeemed at index 0 | Zeros satisfy the ordinary `keccak^k(p) == chain_root` check; no preimage hashes to `0` at any higher index, so the voucher is cryptographically sealed at `amount`. No contract branch, no optional field. |

Signed voucher becomes `{pool_id, signer, provider, amount, bytes_delivered, chain_root,
chunk_price}`. `chain_length` and `chunk_bytes` stay **out** of the signature as protocol
constants.

## The two concurrency rules (the maintainer's open ask)

The comment on #1670 flagged that PayWord's positional encoding is incompatible with
ADR 005's "voucher on any active stream" routing, and asked for an explicit decision. The
issue body resolves it as **option (b) — ticks carry a chain index** — plus a second rule
the earlier draft never wrote down. Both must land, in ADR 003 § Concurrent Streams and
ADR 005 § Payment lanes:

1. **Deepest-preimage-wins merge.** The node keeps the deepest verified preimage (`tip`)
   and its index (`verified`). On a reveal at `index`: ignore it without hashing if
   `index ≤ verified`; reject before walking if `index − verified` exceeds the remaining
   chain; otherwise accept when `keccak^(index − verified)(preimage) == tip`. Arrival
   order across streams is therefore irrelevant within one chain epoch.
2. **Per-stream epoch anchoring.** `index` is mod 256 and a bare reveal does not name its
   chain, so the *only* thing that tells the node "these reveals belong to `R₁`" is the
   signed voucher carrying `R₁`. QUIC gives per-stream ordering, so the invariant is:
   **on each stream, the epoch's `chain_root` voucher precedes that stream's preimages for
   that epoch.** The payer sends it at stream open and again on each roll — not before
   every preimage, which would delete PayWord's point. Resends are cumulative and signed,
   so the node keeps the max and dedup is free. One shared chain and one global counter
   survive; the buyer serializes the counter and the roll decision under a local lock.

## Files to change

### `adr/003-payments.md` — the substance

Written in ASD-STE100 (short sentences, active voice, present tense), matching the file's
existing conventions: bolded lead-in sentences, RFC 2119 keywords in caps, inline code for
every identifier, `§`-style cross-ADR links, bare-anchor intra-document links.

**New sections**, placed between `### Deposit Economics` and `### Credit Window`:

- `### Chunk Cadence` — `chunk_bytes` is 1 MiB and a protocol constant, not a knob; why a
  constant rather than a negotiated parameter (payer and node must agree on what a
  released preimage is worth, and the contract cannot learn which value they used);
  `chunk_price` ≡ `rate_per_mb`; node sovereignty is unchanged and needs no wire field.
- `### Hash-chain metering (PayWord)` — the one formula, the mechanics
  (`chain_root = keccak^255(s)`, release `keccak^(255−k)(s)` after chunk `k` verifies), and
  why a preimage costs one hash with no signature, no ack, no round trip, nothing to
  persist. Subsections:
  - `#### Two payment resolutions` — the preimage/`amount` table (bulk vs exact), and the
    transfer-shape table (small / large-cooperative / large-abandoned).
  - `#### The sealed voucher (zero-hash root)`.
  - `#### Chunk sizing and the payability floor` — the 100 KB / 1 MiB / 10 MiB table
    against target and floor prices; ties the floor to the existing `deliveryFloor`.
  - `#### One chain per lane` — the MUST rules: an independent seed and root per
    `(pool_id, signer, provider)` lane; no reuse across providers, pools, or sibling
    signers; a node MUST reject a root it has seen on another lane or retired on this one.
  - `#### Chain length and rollover` — `MAX_CHAIN_LENGTH = 255`, why the wire byte sets it,
    "the byte is the index", and how a roll folds the exhausted chain into the next
    voucher's `amount`.

**Existing sections to revise:**

- `## Decision` (L25, L38) — voucher field list gains `chain_root` and `chunk_price`; the
  "4 MiB per voucher" key parameter becomes the 1 MiB payment quantum plus chain
  amortization.
- `### Credit Window` (L64–82) — retarget the floor from one 4 MiB voucher interval to one
  1 MiB chunk. Keep #1669's ramp verbatim in shape:
  `min(credit_max, max(chunk_bytes, paid / credit_ramp_divisor))`. Update the defaults
  paragraph, the takedown-latency paragraph, and the durability paragraph (which now points
  at chain state as well as the amount watermark). **Do not restate or re-litigate the ramp
  itself — #1669 owns it.**
- `### Concurrent Streams` (L117–126) — lane-wide chain and index; the two rules above,
  stated as the net invariant; a worked example at 1 MiB.
- `### Redemption and Close` (L128–153) — step 3 gains claim resolution (require
  `chainIndex ≤ MAX_CHAIN_LENGTH`, walk the preimage forward, `claimed = amount +
  chainIndex × chunkPrice` over `claimedBytes = bytesDelivered + chainIndex × CHUNK_BYTES`);
  step 4's `desired` is computed from `claimed`; the rate floor applies to the
  chain-extended values. **Preserve main's current batch semantics** — grouping by pool,
  skip-not-revert for a zero-paying voucher, one `FeeRouter.routeSettlement` per batch.
  A bad preimage or an over-long index joins the structurally-invalid class that reverts
  the whole call, alongside a bad signature. Add the honest gas paragraph: the walk is
  **fallback-only** (a sweep redeems the latest signed voucher — roll or close — and never
  touches a preimage; a walk happens only when the payer vanishes mid-chain), and what is

- `### Off-chain Voucher Rejections (Wire Encoding)` (L175–193) — four new table rows:
  `BadPreimage`, `ChainIndexTooLarge`, `UnanchoredPreimage` (a reveal arrived on a stream

- `#### Voucher withholding` (L221–233) — the per-lane bound drops from 4 MiB to 1 MiB;

  `claimed − paid` still neutralizes resubmission.
- `#### Off-chain voucher state persistence` (L352–368) — the in-memory lane record becomes
  `(last_amount, last_bytes_delivered, chain_root, highest_index)`. Losing chain state on a
  crash forfeits chunks metered since the last signature — the node's own loss, the safe
  direction. **Keep #1672's frontier/redeemed split intact.**
- **New** `#### Cross-lane preimage spend` under `### Node-side` — the adversarial framing
  of root reuse: a shared root makes every preimage released to node A a valid extension of
  node B's voucher; no node and no contract can detect it; the defence is the payer-side
  MUST plus node-side root-reuse rejection.
- `### PaymentPool` contract-interface block (L372–436) — `LaneVoucher` gains `chainRoot`,
  `chunkPrice`, and the redeem-time `chainIndex` / `preimage`. State the calldata cost
  honestly against the existing "160 bytes, static struct" argument at L690.
- **New** `#### Chain walk and redemption cost` under Contract Interfaces — ≤255 keccaks
  (~16k gas at full depth) confined to the abandonment path; a zero root is 32 zero bytes
  and nearly free on compressing L2 calldata.
- `### EIP-712 Voucher Signature` (L658–675) — typehash and digest gain
  `bytes32 chainRoot,uint256 chunkPrice`. Note this is a signed-field change (ADR 013 §
  Signed Field Freezing → Tier 3) taken as a straight pre-launch wire cut per CLAUDE.md.
- `### Voucher ordering` (L696–698) — signed vouchers still order by cumulative `amount`;
  preimages order by chain index, deepest wins.
- `## Decimal Handling` (L984–990) and `### Voucher Bytes-Delivered Field` (L994–1003) — the

- `## Consequences` — positive: no per-chunk signature and no per-chunk durable commit;
  O(1) signatures per transfer. Negative: a preimage is a bearer instrument that demands
  per-lane root discipline; the voucher carries two more signed fields; the meter is
  1 MiB-grained because the token cannot price a finer tick.

## Follow-up to file after merge

**One issue, not three.** The earlier attempt split implementation across #1693 / #1694 /
#1695 and all three were closed; the signed field set, the wire message, and the contract
walk cannot land independently anyway — a voucher that gains `chain_root` breaks the `sol!`
mirror, the typehash pin, and the wire encoding in the same change. File a single
`feat(payments)` issue covering the whole cut, with the three layers as a checklist inside
it and links to the merged ADR anchors:

- **`crates/protocol`** — `ChunkPreimage { preimage, index }` wire message and its
  `ClientMessage` variant renumbering, `CHUNK_BYTES` / `MAX_CHAIN_LENGTH` constants, and
  the four new `VoucherRejectReason` variants.
- **`crates/incentive`** — `chain_root` / `chunk_price` in the EIP-712 `Voucher` and its
  `sol!` mirror, lane chain state (`chain_root`, verified index), per-lane seed derivation,
  and deepest-preimage verification in `LaneState::apply_voucher`'s sibling path.
- **`contracts`** — `LaneVoucher` fields plus the redeem-time `chainIndex` / `preimage`,
  the bounded chain walk in `redeemMany`, `BadPreimage` / `ChainIndexTooLarge`, and the
  `InterfaceFreeze.t.sol` typehash pin.

Note in the issue that #1693–#1695 are superseded by it.
